# Project Instructions

## Repository Context

This repository is Agent Template Kits: a template source for installing agent engineering assets into other projects. It is not a deployable application.

## Repository Layout

| Path | Purpose |
| --- | --- |
| `profiles/` | Built-in agent layout contracts in YAML. |
| `templates/` | Installable rules, hooks, and seed files for self-learning, env, and cache components. |
| `skills/` | Distributable skill packages. |
| `scripts/` | Repository-level tooling such as install, validation, docs checks, and runtime skill sync. |
| `.agents/skills/` | Codex runtime skill mirror for this repository, synced from canonical sources. |
| `.codex/` | This repository's Codex rules, hooks, scripts, and workflows. |
| `.claude/skills/` | Claude Code runtime skill mirror for this repository. |
| `.agent-sync/` | Multi-agent sync runtime. |
| `tests/` | Regression and quality guard tests. |
| `docs/` | Portability docs, design plans, and user-facing documentation. |
| `.learnings/` | Self-learning records and distilled rules. |

## Core Workflows

### Add an Agent Profile

1. Create a YAML file under `profiles/` based on the existing profile schema.
2. Include `name`, `description`, `agent_dir`, `skills_dir`, `rules_dir`, `scripts_dir`, `hooks_dir`, `entry_file`, `hook_config`, `hook_template`, `include_openai_yaml`, `env_template`, `skill_registry`, and `prompt_cache_rule`.
3. Update the profile tables in `README.md` and docs.
4. Validate with `python3 scripts/validate-profiles.py`.

### Add a Skill

1. Create `skills/<skill-name>/` as the canonical distributable source.
2. Include `SKILL.md`; add `scripts/`, `references/`, `assets/`, and `agents/openai.yaml` only when useful.
3. If the skill should be distributed across profiles, add it to the appropriate sync scope.
4. Run `python3 scripts/sync-runtime-skills.py` to update `.agents/skills/`.
5. Update `README.md` and docs.

### Release

1. Update `CHANGELOG.md`.
2. Ensure `./scripts/validate.sh` passes.
3. Tag and push the release.

## Coding Conventions

- Python targets 3.10+, with type annotations, `pathlib.Path`, and f-strings.
- Bash scripts use `#!/usr/bin/env bash` and `set -euo pipefail`.
- YAML profile files are UTF-8 and do not use tabs.
- Markdown docs in Chinese should stay Chinese; `SKILL.md` files should stay English.
- Use `/` paths for portability and avoid relying on `~` expansion.
- Hook scripts are Python 3 and generate host-local config through bootstrap scripts.
- Security audit output must never include raw secret values.
- Installers default to dry-run or non-destructive behavior unless an explicit apply or overwrite flag is given.

## Key Conventions

- `.codex/hooks.json`, `.claude/settings.json`, `.codebuddy/settings.json`, and `.agent-sync/local/` are host-local gitignored files generated by bootstrap.
- After a fresh clone, run `python3 .agent-sync/scripts/bootstrap.py --apply` when `.agent-sync/` is installed.
- `scripts/install.py` previews by default; use `--apply` to write changes.
- Skill registries preserve manually added external entries.
- After workflow routing changes, run `.codex/scripts/sync-workflow-routing.sh --check`.
- `validate.sh` is the main CI quality gate for push and PR checks.

## Self-Learning

- Before task work, apply `.learnings/RULES.md`, `.learnings/ERRORS.md`, and recent `.learnings/LEARNINGS.md`.
- Codex loads the learning reminder through `.codex/hooks/read_learnings.py`. After a fresh clone, install `.agent-sync` and run its `bootstrap.py --apply` command to create the ignored `.codex/hooks.json` for the current host.
- Record real recurring mistakes or reusable lessons in `.learnings/`, but fix the source skill, template, hook, script, or project rule before archiving resolved records.
- Shared Codex skills live under `.agents/skills/`. Keep their distributable source in sync with:

```bash
python3 scripts/sync-runtime-skills.py --check
```

- Cross-profile configuration synchronization belongs to `multi-agent-sync`. When `.agent-sync/` is installed, preview with `python3 .agent-sync/sync_agents.py --check --scope skills` and apply only the affected scope.

## Workflow Todo State

Named workflow state files are the source of truth for every routed workflow.

- Workflow definitions live under `.codex/workflows/{workflow-id}/`.
- Workflow state files live under `workspace/workflow-runs/` and should be named after the task, for example `payment-refactor.workflow.md`.
- Before any action that changes project files, runs project commands, or calls external services, read `.codex/rules/workflow-routing.md` and match the user's original request against its triggers and exclusions.
- When a `Required: yes` workflow matches, read its `workflow.md`, create or resume its state file, and start the current phase before doing the work. Do not take the ordinary execution path instead.
- If the route is ambiguous, ask the user before acting.
- Read the active workflow state file before starting any phase; do not skip prerequisite phases.
- Change phase state only through `.codex/scripts/todo-state.sh`.
- Use one unique phase status line per phase, for example `> [P0] ⬜ 未开始`.
- On resume after interruption, inspect the YAML frontmatter and current phase before acting.
- Each workflow directory must contain a `routing.yaml`. After creating, changing, renaming, or deleting a workflow, run `.codex/scripts/sync-workflow-routing.sh`; the update is incomplete until `.codex/scripts/sync-workflow-routing.sh --check` passes.

## Environment Variables

- Follow `.codex/rules/common/env.md` whenever creating, updating, migrating, or auditing `.env`, `.env.example`, or environment-variable documentation.
- Keep committed env templates minimal, project-specific, and free of real secrets or machine-local absolute paths.
- After env template changes, run `.codex/scripts/check-env-template.sh`. Use `--strict` when you want unused documented variables to fail the check.
